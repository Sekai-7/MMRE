一、 业务需求与系统定位 [绝对基准]引擎作为智能座舱底软系统的核心中间件，旨在解决全场景理解下多模态数据的整合与查询问题。1. 系统上下游关系与边界引擎定位：基于时间线的多模态资源引擎位于整个系统的资源层核心位置 。上游连接：向下承接底层 Resource Provider（如摄像头、麦克风、车辆信号等提供者）作为数据输入源 。下游连接：向上层 Agent（包含 System Agents, OEM Agents, Central System Agent）和 Local MCP 提供基于时间线的数据查询接口 。控制关系：在系统初始化时，Agent 层会根据业务场景需求配置 Resource Manager，告知所需数据源及触发规则 。引擎在预定义规则下，可主动触发上层 Agent 工作 。2. 多模态数据类型与同步目标引擎必须支持以下多模态数据的基于时间线的缓存与统一管理：Vehicle Signal (车辆信号)：数据格式为 Key-Value 结构 。具备 Groupable 属性，不同信号可关联描述同一组功能 。具备 Explainable 属性，支持通过插件解读为大模型可理解的文本描述 。Camera (视觉/视频流)：支持 Multiple Camera Stream（多路摄像头流） 。数据格式为带时间戳的图像帧 。必须通过共享内存方式管理 。System Agent 可生成特定文本描述来取代帧图像存储 。Audio (音频流)：支持 Multiple Microphones stream（多路麦克风流） 。数据格式为带时间戳的 PCM 数据，长度由语音激活时长决定，可被 Provider 截断 。System Agent 可生成特定文本取代语音存储 。Screen Capture (屏幕捕获)：支持 Multiple Screens（多屏幕数据） 。数据格式为 BPM/PNG/JPEG 图像 。必须通过共享内存方式管理 。System Agent 可生成特定文本描述取代帧图像存储 。System Log (系统日志)：数据格式为 Module-Log 。具备 Explainable 属性，支持插件解读为大模型可理解的文本描述 。System Agent 可生成特定系统状态描述文本作为 log 存储 。3. 时间线 (Timeline) 工作机制要求时序对齐：必须支持多模态数据的时间对齐处理 。数据以时间序列的方式填充在紧凑的缓存中 。灵活查询：支持当前时刻（Tx）查询以及历史时刻（Tx-n）回溯查询 。默认查找指定时刻 1s 内的数据的最新状态，该 1s 间隔时长可配置 。持久化同步 (Sync)：当缓存数据超过指定大小或时间，须同步到持久化存储（UFS） 。精简存储与抽帧：支持按照预定规则和检查点（Checkpoint）时刻采样的方式精简数据到持久分区 。例如，对 Camera 视频流按固定时间抽帧，或按检查点抽帧 。检查点机制 (Checkpoint)：检查点是时间线上的特定标记时刻，通常代表关键状态或场景变化 。支持智能体层设置检查点，支持触发器设置检查点，并支持检查点 list 查询 。主动触发机制 (Trigger)：支持配置车辆信号或资源捕获的触发规则 。当状态转换规则发生时，系统能主动通过事件通知智能体层 。二、 运行环境与非功能性约束 [绝对基准]1. 软硬件运行环境硬件平台：系统明确要求运行在 QC8397/CX1 硬件平台上 。存储介质：缓存持久化目标介质为 UFS (Universal Flash Storage) 。2. 性能、并发与延迟指标并发规模条件：测试基准设定为资源数量为 5，Vehicle 信号数量不超过 100 。查询延迟要求：缓存（Cache）中的全类型资源查询和单资源查询响应时间不超过 10ms 。持久化存储（UFS）中的查询响应时间不超过 100ms 。写入延迟要求：单个文本和信号资源的写入时间不超过 1ms 。单个复杂存储资源（如视频帧、音频段）的写入时间不超过 5ms 。扩展性：系统必须做到资源数据类型可扩展 。三、 暂定架构设计与模块划分 [可变参考]以下提取自《SA24225109邓杰提交版2.pdf》，为实现上述 [绝对基准] 而构思的具体软件架构、数据结构与流程。（注意：若后续与性能指标或核心基准冲突，允许被推翻和重构）1. 系统逻辑分层 (参考设计)系统逻辑被划分为四个核心层级 ：控制平面 (Control Plane)：由 Resource Manager 主导，负责策略管理、通信接口路由、指令权限校验和生命周期管理 。服务接口层 (Service Interface Layer)：包含 InterfaceParser、BaseQuery 等，负责将来自不同协议的外部请求（Native API, SQL, RPC/IPC）归一化为内部标准查询对象 。核心引擎层 (Core Engine Layer)：包含 MultiResource TimelineCache（核心缓存）、PersistenceEngine（异步持久化）、CheckpointManager（检查点管理）、TriggerManager（触发器引擎） 。资源适配层 (Resource Adaptation Layer)：包含 Resource Provider HAL、Data Ingestion Manager（数据摄入）、Shared Memory Manager（共享内存管理），负责底层异构数据的抽象接入 。2. 核心数据结构与内存管理 (参考设计)Timeline Cache 混合索引结构：采用“红黑树 (Red-Black Tree) + 双向链表”混合结构 。红黑树：作为一级索引，以时间戳为键值，保障插入/查询的 O(log N) 复杂度 。双向链表：连接叶子节点，将范围时间窗查询复杂度优化为 O(log N + K) 。分级内存池机制 (Slab & Shared Memory)：高频小对象（如 CAN 信号）：采用固定块大小的内存池 (Slab Allocation) 管理，消除内存碎片与系统调用开销 。大对象（如视频流）：基于引用计数的共享内存管理。分配连续物理内存池，底层仅传递包含内存偏移量、大小及引用计数的句柄（Handle）。仅当引用计数归零且完成持久化时，物理内存才被回收，实现全链路零拷贝 (Zero-Copy) 。3. 并发模型与实时性保障 (参考设计)Reactor 混合线程模型：分离 I/O 线程与工作线程。数据接入层采用基于 epoll 的单 I/O 线程 (IO-Reactor) 仅处理连接与二进制流接收 。后端维护固定大小的工作线程池 (Worker Pool) 执行解码、对齐、内存分配等耗时操作 。无锁环形队列 (Lock-free Ring Buffer)：作为 I/O 线程与工作线程之间的缓冲区，基于 std::atomic 原子操作与内存屏障实现单生产者-单消费者无锁入队/出队 。多粒度分段锁机制：废弃全局锁，对 TimelineCache 内部不同资源类型（Camera, Audio, VehicleSignal）采用独立的互斥锁（基于 ResourceType 的哈希映射表），实现写入并发隔离 。查询快慢路径分离：快路径 (Fast Path)：针对热点数据，RPC 线程申请共享读锁，因历史时间桶不可变，实现近乎无锁的同步直读，直接返回共享内存句柄 。慢路径 (Slow Path)：针对冷数据或复杂后处理，将请求封装为异步任务卸载至 Query Worker Pool，工作线程通过 mmap 建立文件映射进行处理，处理完毕通过回调返回新句柄，防止阻塞核心线程 。4. 数据生命周期与核心业务流 (参考设计)数据包 (UnifiedDataPacket) 的生命周期被抽象为确定的状态机 ：暂态 (Created)：通过 DataIngestionManager 接入，完成时间戳对齐 。活跃态 (Active/Hot)：数据节点挂载至 TimelineCache，大载荷数据通过共享内存句柄进入驻留态，对外提供检索 。待持久化态 (Dirty)：依据策略（如 LRU/容量阈值），数据被标记 。持久化态 (Persisted/Cold)：PersistenceEngine 异步介入，执行抽帧/降采样后写入 UFS 。驱逐与消亡态 (Evicted/Destroyed)：内存空间不足时从内存树移除节点；仅当共享内存引用计数彻底归零时，释放物理内存 。5. 混合 IPC 通信架构 (参考设计)为屏蔽底层传输协议差异，设计统一的抽象层（IServer） ：Native IPC (本地通信)：针对同计算单元的 Agent，基于 Unix Domain Socket 实现。控制指令走 Socket，数据载荷走共享内存句柄 。FDBus RPC (远程通信)：针对跨域交互（如 IVI 与 ADAS），将请求封装在 FDBus payload 中进行网络透明传输 。
