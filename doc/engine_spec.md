# 一、业务需求与系统定位（绝对基准）

引擎作为智能座舱底软系统的核心中间件，旨在解决全场景理解下多模态数据的整合与查询问题。

## 1. 系统上下游关系与边界

**引擎定位：**\
基于时间线的多模态资源引擎位于整个系统的资源层核心位置。

**上游连接：**\
向下承接底层 Resource
Provider（如摄像头、麦克风、车辆信号等提供者）作为数据输入源。

**下游连接：**\
向上层 Agent（包含 System Agents、OEM Agents、Central System Agent）和
Local MCP 提供基于时间线的数据查询接口。

**控制关系：**\
在系统初始化时，Agent 层会根据业务场景需求配置 Resource
Manager，告知所需数据源及触发规则。\
引擎在预定义规则下，可主动触发上层 Agent 工作。

------------------------------------------------------------------------

## 2. 多模态数据类型与同步目标

引擎必须支持以下多模态数据的基于时间线的缓存与统一管理：

### Vehicle Signal（车辆信号）

-   数据格式为 Key-Value 结构\
-   具备 Groupable 属性，不同信号可关联描述同一组功能\
-   具备 Explainable 属性，支持通过插件解读为大模型可理解的文本描述

### Camera（视觉 / 视频流）

-   支持 Multiple Camera Stream（多路摄像头流）\
-   数据格式为带时间戳的图像帧\
-   必须通过共享内存方式管理\
-   System Agent 可生成特定文本描述来取代帧图像存储

### Audio（音频流）

-   支持 Multiple Microphones stream（多路麦克风流）\
-   数据格式为带时间戳的 PCM 数据，长度由语音激活时长决定，可被 Provider
    截断\
-   System Agent 可生成特定文本取代语音存储

### Screen Capture（屏幕捕获）

-   支持 Multiple Screens（多屏幕数据）\
-   数据格式为 BPM / PNG / JPEG 图像\
-   必须通过共享内存方式管理\
-   System Agent 可生成特定文本描述取代帧图像存储

### System Log（系统日志）

-   数据格式为 Module-Log\
-   具备 Explainable 属性，支持插件解读为大模型可理解的文本描述\
-   System Agent 可生成特定系统状态描述文本作为 log 存储

------------------------------------------------------------------------

## 3. 时间线（Timeline）工作机制要求

**时序对齐**\
必须支持多模态数据的时间对齐处理。

**数据组织**\
数据以时间序列方式填充在紧凑的缓存中。

**灵活查询** - 支持当前时刻（Tx）查询 - 支持历史时刻（Tx-n）回溯查询 -
默认查找指定时刻 1s 内数据的最新状态（该间隔可配置）

**持久化同步（Sync）** -
当缓存数据超过指定大小或时间，须同步到持久化存储（UFS）

**精简存储与抽帧** -
支持按照预定规则和检查点（Checkpoint）时刻采样方式精简数据 - 例如 Camera
视频流按固定时间抽帧或按检查点抽帧

**检查点机制（Checkpoint）** - 检查点是时间线上的特定标记时刻 -
代表关键状态或场景变化 - 支持智能体层设置检查点 - 支持触发器设置检查点 -
支持检查点 list 查询

**主动触发机制（Trigger）** - 支持配置车辆信号或资源捕获触发规则 -
当状态转换规则发生时，系统主动通过事件通知智能体层

# 二、运行环境与非功能性约束（绝对基准）

## 1. 软硬件运行环境

**硬件平台：**\
系统要求运行在 QC8397 / CX1 硬件平台。

**存储介质：**\
缓存持久化目标介质为 UFS（Universal Flash Storage）。

------------------------------------------------------------------------

## 2. 性能、并发与延迟指标

**并发规模条件** - 资源数量基准：5 - Vehicle 信号数量不超过：100

**查询延迟** - Cache 查询（全类型资源 / 单资源） ≤ 10ms - UFS 查询 ≤
100ms

**写入延迟** - 文本 / 信号资源写入 ≤ 1ms - 视频帧 / 音频段等复杂资源 ≤
5ms

**扩展性** - 系统必须支持资源数据类型可扩展

------------------------------------------------------------------------

## 2. 核心数据结构与内存管理

### Timeline Cache 混合索引结构

结构：

**红黑树（Red-Black Tree）** - 以时间戳为键 - 插入 / 查询复杂度 O(logN)

**双向链表** - 连接叶子节点 - 时间窗口查询复杂度 O(logN + K)

------------------------------------------------------------------------

### 分级内存池机制

**Slab Allocation（小对象）** - 适用于 CAN 信号 - 固定块大小 -
消除内存碎片

**Shared Memory（大对象）** - 视频流 - 音频流

设计：

-   连续物理内存池
-   仅传递句柄（Handle）

句柄包含：

-   内存偏移
-   数据大小
-   引用计数

当：

-   引用计数归零
-   持久化完成

才释放物理内存。

实现：

**全链路 Zero-Copy**

------------------------------------------------------------------------

## 3. 并发模型与实时性保障

### Reactor 混合线程模型

**IO Reactor** - 单 I/O 线程 - 基于 epoll - 处理连接与数据接收

**Worker Pool** - 固定大小线程池 - 处理： - 解码 - 时间对齐 - 内存分配

------------------------------------------------------------------------

### Lock-free Ring Buffer

作用：

-   IO 线程 → Worker 线程通信

技术：

-   std::atomic
-   memory barrier

模型：

**Single Producer Single Consumer**

------------------------------------------------------------------------

### 多粒度分段锁

取消：

-   全局锁

改为：

-   ResourceType 维度锁

例如：

-   Camera lock
-   Audio lock
-   VehicleSignal lock

实现：

并发写入隔离。

------------------------------------------------------------------------

### 查询快慢路径

**Fast Path**

-   热数据查询
-   RPC 线程获取共享读锁
-   历史时间桶不可变
-   直接返回共享内存句柄

**Slow Path**

-   冷数据 / 复杂查询
-   请求进入 Query Worker Pool
-   Worker 使用 mmap 映射文件
-   处理后返回新句柄

------------------------------------------------------------------------

## 4. 数据生命周期

UnifiedDataPacket 生命周期：

**Created** - DataIngestionManager 接入 - 完成时间对齐

**Active / Hot** - 节点进入 TimelineCache - 数据驻留共享内存

**Dirty** - 满足 LRU / 容量阈值

**Persisted / Cold** - PersistenceEngine 异步写入 UFS - 可能执行抽帧 /
降采样

**Evicted / Destroyed** - 从内存树移除 - 当引用计数为 0 时释放物理内存

------------------------------------------------------------------------

同计算单元 Agent
